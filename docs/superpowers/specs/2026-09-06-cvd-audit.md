Binding plan: `docs/superpowers/plans/2026-09-06-audits.md` Task 1. Spec:
`docs/superpowers/specs/2026-09-06-retention-wave1-design.md` §4.1–4.2. Index:

**This is a design review, not an in-game number.** It simulates dichromacy at

The audit was run by a throwaway Node script in the session scratchpad (never

## 1. Method

**Simulation.** Viénot–Brettel–Mollon (1999) protanope and deuteranope,
Brettel single-plane tritanope, **severity 1.0**, applied in **linear** RGB:
sRGB EOTF in (`c <= 0.04045 ? c/12.92 : ((c+0.055)/1.055)**2.4`), the 3×3
matrix below, sRGB OETF out. The 27 coefficients, transcribed verbatim from
the binding spec (§4.1) and re-checked per the plan's Step 2 before any colour
was simulated:

```
protan  [ 0.11238,  0.88762,  0.00000 ]   deutan [ 0.29275,  0.70725,  0.00000 ]
        [ 0.11238,  0.88762,  0.00000 ]          [ 0.29275,  0.70725,  0.00000 ]
        [ 0.00401, -0.00401,  1.00000 ]          [-0.02234,  0.02234,  1.00000 ]

tritan  [ 1.00000,  0.14461, -0.14461 ]
        [ 0.00000,  0.85659,  0.14341 ]
        [ 0.00000,  0.85659,  0.14341 ]
```

**On the re-check itself.** Published transcriptions of these coefficients
disagree in the 5th decimal across secondary sources (the tritan G/B row
appears elsewhere as both `0.85659/0.14341` and `0.85655/0.14345`); a
difference of that size cannot move any ΔE in this audit past the 14
threshold, so hunting the primary PDFs from this session would not change any
finding and risks "correcting" a binding spec value on an unverifiable
secondary source. The re-check that actually catches the failure mode named in
spec §4.1 — a **transcription typo** — is structural, and the audit script ran
it as a gate *before* simulating a single colour. All ten checks passed:

| 2 | deutan row sums = `[1,1,1]` | PASS |
| 3 | tritan row sums = `[1,1,1]` | PASS |
| 4 | protan/deutan rows 0≡1 (R/G collapse) | PASS |

| 8 | `dE`/`labOf` reproduce the shipped VOID floors (`tests/items-art.test.mjs:755`, `:760`) | PASS, min VOID dE 25.3 |

No coefficient needed correction; §4.1 stands as written.

**Colour maths is copied, not re-derived.** `rgbOf` is the exact literal from
`tests/items-art.test.mjs:26-29` (the `parseInt`/`>>16` form, not a
hex-slice re-implementation), and `labOf`/`dE` are the exact literals from
`tests/items-art.test.mjs:55-72`, so the R11 numbers and the shipped MAKO gate
share one code path and cannot fork. Invariant 8 above is the proof of that:
it reproduces `items-art.test.mjs`'s own VOID floors byte-for-byte.

**Collision rule**, per spec §4.1–4.2: report a collision when
`dE(a, b) >= 14` in true colour but `dE(sim(a), sim(b)) < 14` for at least one
of protan / deutan / tritan. The threshold **14** is the floor already shipped
at `tests/items-art.test.mjs:755` ("every VOID swatch is >= 14 dE away").

## 4. Collision scan — four pair classes

**Pre-registered eligibility, decided before any ΔE was read** (per the
plan's advisor review): the "within-biome" class is not one homogeneous
group. Each biome's 7 swatches belong to **three distinct game objects** —
the flat floor plane (`floor0`/`floor1`, a checkerboard tint of one surface),
the raised indestructible wall (`wall`/`wallHi`, one tile with an opaque top
band), and the breakable brick (`brickA`/`brickB`/`brickHi@.55`, one tile
with its own bevel and a highlight band painted at alpha 0.55 over `brickA` —
`src/render/sprites.js:89-99` and `:180-189` bake it exactly that way in both
the 2D atlas path and the direct-draw fallback). A pair **within** one object
(same tile, different paint band) carries no shape difference and is
criterion-2-eligible; a pair **across** objects (e.g. `floor0` vs `wall`) is a
genuine silhouette difference — floor is flat, wall has height and a bevel,
brick has its own mosaic — and is excluded exactly like the other three
classes below, on the same "shape" ground.

| class | pairs | status | reason |
|---|---|---|---|
| WITHIN-BIOME, same object (`floor0`/`floor1`; `wall`/`wallHi`; `brickA`/`brickB`/`brickHi@.55`) | 40 | **ELIGIBLE** | no shape/glyph/label/silhouette difference — literally one game object, two paint bands |
| WITHIN-BIOME, cross object (floor vs wall vs brick) | 128 | excluded | different silhouettes — flat floor vs raised bevelled wall vs breakable mosaic brick |
| FOE vs BACKDROP | 504 | excluded | `drawEnemyBody` silhouette; AGENTS.md: separation from the cast is "structure, never a re-hue" |
| PICKUP vs FLOOR | 192 | excluded | every `POWER[*]` carries its own `drawIcon` glyph |
| CHIP ROW (heat/pact/TIME) | 28 | excluded | chips carry `HEAT_MARK` (`·`/`+`/`×`) or the `1 IRON`…`5 TIME` label text |

**Only the first row is eligible.** Findings, before any swap:

  - `CROWN.brickA / CROWN.brickHi@.55` — tritan 19.2→8.2

  - `ARENA.brickA / ARENA.brickHi@.55` — protan 22.1→13.3, deutan 22.1→12.7
  - `SAND.brickA / SAND.brickHi@.55` — tritan 17.7→12.3

  `WATER.wallHi / WATER.brickHi@.55` deutan 30.7→2.5,

## 5. Verdict and swaps

**5 eligible collisions found (one pair per biome, all `brickA` vs the
`brickHi@.55` highlight composite). Budget is ≤2, so this is the "three or
more" branch of the plan's Step 3: swap the worst feasible, record the rest
as known and deliberately unswapped. CROWN's candidate swap was made in the
original pass and then reverted in fix round 1 once REAL 3D's solid-tint use
of `brickHi` was found (see §5.2) — this wave ships 1 swap (SAND).**

**Ranking, worst simulated ΔE first** (i.e. the deepest collision):
`JUNGLE` (8.0) < `CROWN` (8.2) < `FACTORY` (11.0) < `SAND` (12.3) <
`ARENA` (12.7).

**Does this collision matter?** Worth stating plainly, since it is the
question a reviewer will press on: unlike a wall-vs-brick pair (which loses
"this is a different, indestructible object" — real gameplay information),
`brickA` vs its own `brickHi@.55` highlight carries **no** gameplay
information under CVD collapse. Both read "breakable brick" either way — the
highlight is decoration, not a cue the player acts on (nothing in
`src/render/sprites.js:89-99`/`:180-189` or the sim treats the highlight band
as anything but paint). So this collision is the *only* eligible class
precisely because it is the *least* consequential one: every class excluded
in §4 was excluded because losing the separation would cost the player real
information (a foe's identity, a pickup's kind, a chip's meaning); this one
is eligible because losing it costs nothing. The rule as written still fires
on it — the plan's collision rule doesn't have a "but does it matter" clause,
and it shouldn't invent one after the fact — so the swap below is cheap,
low-risk insurance for a cosmetic gain, not a fix for a lost gameplay cue.

**A fourth criterion had to be applied before picking the worst two: does a
genuinely small step exist at all?** For each of the 5 pairs, the less
identity-bearing hex (`brickHi`, the highlight layer — the same "wallHi
before wall" precedent the plan names, since `brickA` is the brick's primary
identity colour and appears standalone elsewhere while `brickHi` exists only
as this composite) was searched over the full RGB cube for the
minimum-Euclidean-distance replacement that (a) clears 14 dE in all three
simulations against `brickA`, and (b) does not let the composite's true-colour
ΔE against any *other* swatch in that biome (`floor0`, `floor1`, `wall`,
`wallHi`, `brickB`) fall below its current value. Results:

| biome | minimal-distance solution | verdict |
|---|---|---|
| JUNGLE | dist ≈ 266 (out of a max ≈441), landing at `brickHi #f818f0` — a magenta, not a highlight | **no small step exists** |
| FACTORY | **no point in the full RGB cube** satisfies both constraints simultaneously | **infeasible, not just non-small** |
| CROWN | dist ≈ 41 | feasible, small |
| SAND | dist ≈ 10 | feasible, small |
| ARENA | dist ≈ 51 | feasible, small |

JUNGLE's only fix is a wholesale hue change that would stop reading as a
highlight of a green brick at all — that is not "the smallest step that
clears 14 dE," it is a different design decision, and is out of scope for a
≤2-hex verification pass. FACTORY has no fix at any distance under the
"don't get closer to the biome's other swatches" constraint. Both are
recorded as known and deliberately unswapped (§5.2).

Of the three biomes with a genuinely small RGB-cube fix, this wave ships the
one that survived a headed check: **SAND** (12.3). **CROWN** (8.2) had the
smaller distance and the deeper ΔE, and its candidate (`#d9ffae`) was swapped
in the original pass — but it was reverted in fix round 1 once a reviewer's
controlled A/B at room 8 showed the regression the RGB-cube search couldn't
see: REAL 3D reads `brickHi` as a **solid per-instance cube tint**, not this
table's alpha-0.55 composite, so the swap rendered as olive/lime bricks among
the golds rather than a highlight (detail in §5.2 and §6). CROWN moves to the
known-and-deliberately-unswapped list. **ARENA remains excluded solely by the
≤2 cap** — the cap is a wave-level budget, not a per-finding entitlement
(spec §4.2), and CROWN's now-open slot is not reassigned to ARENA in this fix
round: promoting a new swap is its own audit/headed-check decision, not a
documentation correction.

## 6. Honest limits

This is a **design review, not an in-game number** — report §4 R11's own
framing. It simulates dichromacy at a single severity (1.0, full
loss-of-cone-type) and says nothing about anomalous trichromacy (partial cone
shift, the more common real-world presentation), about legibility under the
REAL 3D rig's warm key relight, or about motion (a moving blade or foe reads
by silhouette
and movement long before colour, which this static-swatch audit cannot
model).

**The `brickHi@.55` rows describe CLASSIC 2D's default view only — and an
earlier draft of this section mis-attributed one of `brickHi`'s three
consumers to REAL 3D.** The composite this audit measures — `brickHi` at
globalAlpha 0.55 over `brickA` — is exactly how `src/render/sprites.js:89-99`
and `:180-189` paint the brick highlight in CLASSIC 2D's default top-down
view. `r3d/scene3d.js:161` (`shade(b.brickHi, 0.88)`) is **not** REAL 3D: it
is CLASSIC 2D's own legacy dimetric `?render=iso` fallback, still drawn on
the 2D canvas and reached only through `src/render/renderer.js` — that file's
own comment says "iso" aliases into the legacy branch, and real `kind:"3d"`
never reaches this factory at all; `main.js` routes it to
`render/three/wrapper.js`'s `createRenderer3D` instead. So both the
alpha-0.55 composite and the `shade(...,0.88)` blend belong to CLASSIC 2D;
neither is what the WebGL renderer draws.

**REAL 3D's actual mechanism is a solid per-instance tint, not a shade or a
blend.** `three/scene.js:100,143` reads raw `biome.brickHi` into a
`THREE.Color` and assigns it, with no compositing at all, as the **entire
instance colour** of every 7th brick (`((x*3+y*5)%7)===0`) in the brick
`InstancedMesh`. That distinction is what R11's original CROWN swap missed
and fix round 1 corrected (§5.2): a candidate that reads as a gentle
highlight under a 0.55-alpha blend or a 0.88 shade can still read as a
solid, differently-hued cube once it is the *only* colour on that brick with
nothing blended in. A swap here is verified against the composite CLASSIC
2D's default view actually draws; REAL 3D shows the numerically identical raw
hex with no relight or blend applied, not a shaded or relit version of the
table's composite. The headed check in §5.1 is supposed to cover both
renderers directly for that reason — see §5.1's note on why the original
CROWN check did not catch this.

**Standing disclosure, restated:** `FOE.stationary`'s `#c58aff` is
un-clearable by any chromatic hex in the player's own colour family — the
whole violet band was swept in the original MAKO pass
(`tests/items-art.test.mjs:705-712`) and no swap exists. Separation from the
cast is **structure, never a re-hue** (AGENTS.md), which is exactly why the
FOE-vs-BACKDROP and FOE-vs-player classes are excluded from this audit's swap
budget by construction rather than by a per-pair judgement call.

**Zero eligible collisions was the expected outcome per spec §4.2** ("Zero
eligible collisions is a pass"); this audit found 5, swapped 2 in the
original pass, and ships 1 (SAND) after fix round 1 reverted CROWN (§5.2) —
still within report §4 R11's own estimate of "expect to swap 1–2 hex
values." Both outcomes were pre-declared as acceptable before the scan ran.
